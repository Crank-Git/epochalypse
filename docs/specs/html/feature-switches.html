Epic 5: Dead man’s switches   built

Dead man’s switches

Purpose

Release replicated encrypted content after missed check-ins despite main-server loss.

User stories

As an owner, I want this feature so that I can verify the release behavior before I trust the deployment.

Functional requirements

  • FR-switches-1: The owner configures a check-in interval and grace period.
  • FR-switches-2: The owner arms a switch only after all three agents confirm durable content.
  • FR-switches-3: The owner sends signed check-ins directly to each agent.
  • FR-switches-4: The interface reports renewal success only after three durable receipts.
  • FR-switches-5: The agents release shares after their accepted deadline plus grace.
  • FR-switches-6: The public recovery client reconstructs a key from two valid release shares.
  • FR-switches-7: The recovery client retrieves ciphertext without the main server.
  • FR-switches-8: The interface reports each agent receipt independently.
  • FR-switches-9: The owner exports a recovery bundle before the switch becomes armed.
  • FR-switches-10: The deployment test stops the main server plus one agent before release.

User flows

flowchart TD
 Draft[Prepare switch] --> Replicate[Copy ciphertext and shares]
 Replicate --> Confirm{Three durable receipts?}
 Confirm -->|No| Unarmed[Show unarmed]
 Confirm -->|Yes| Export[Export recovery bundle]
 Export --> Arm[Arm switch]
 Arm --> Checkin[Send signed check-in]
 Checkin --> Renewed{Three receipts before boundary?}
 Renewed -->|Yes| Arm
 Renewed -->|No| Uncertain[Show B0 through Bmax and agent evidence]
 Arm --> Deadline[Deadline plus grace]
 Uncertain --> Bound[Release by Bmax plus E]
 Bound --> Shares
 Deadline --> Shares[Agents publish permitted shares]
 Shares --> Recover[Recover from two agents]
  1. Choose an interval and grace period.
  2. Replicate the encrypted content to all agents.
  3. Verify the three durable receipts.
  4. Export the recovery bundle.
  5. Arm the switch.
  6. Send check-ins before the deadline.
  7. If renewal lacks a receipt, show B0 through Bmax with the reviewed allowance E.
  8. After release, recover the content from two agents.

Behaviour rules

This feature depends on acceptance of the protocol review. Its rules defer to the reviewed protocol where the review identifies unsafe transitions. Default interval: 24 hours. Default grace: 1 hour. Allow intervals from 1 hour to 365 days. Allow grace from zero to 30 days. Show deadline and grace separately in UTC and the browser's local time. Set a new deadline from the signed check-in issue time plus the configured interval. Before transmission, durably journal the exact signed request, sequence, deadline, and boundary. Retry identical bytes with the same sequence and deadline. Arrival time never extends the deadline. Three matching durable receipts confirm renewal. An incomplete response leaves the outcome uncertain. Show B0 as earliest possible disclosure, not an exact authority for every agent. Show Bmax as the latest already-issued signed boundary. Show the reviewed allowance E separately. Release can precede the proposed boundary or follow B0. The default uncertainty can approach 24 hours. After main loss plus one outage, two reachable, honest agents with intact durable state release by Bmax plus E. The reviewed clock assumptions apply. ADR 0013 accepts candidate E=34 seconds for implementation. Actual-host clock and publication verification remain required before a production bound claim. Reject check-ins whose issue time exceeds the reviewed clock tolerance. A DNS query never renews a switch. Automated main-server check-ins do not establish owner presence. Require an owner signing key for direct check-ins. Store a web-use key only after the owner accepts its weaker host-compromise model. The CLI supports a locally held signing key. Scoped API tokens alone cannot forge direct agent check-ins. Each agent stores a complete ciphertext copy and one distinct key share. The bundle contains all agent endpoints, identities, content digests, and public verification material. Each agent serves public recovery data independently. Public recovery needs no owner authentication. Provide a standalone recovery CLI. Main-server DNS availability is not a recovery dependency. An agent that ever releases a share refuses renewal of the same content key. Count shares retained by observers even when an endpoint removes them. Show release as irreversible. Agent decommission or cancellation requires the reviewed protocol. Use the same 10 MiB content limit and local retention rule as capsules.

Data touched

Switch, agent, share reference, encrypted object, receipt, durable client journal, check-in sequence, audit event. Agents store independent state.

Interfaces

POST /api/v1/switches creates a draft and returns 201. POST /api/v1/switches/{id}/arm returns 200 only after the reviewed arm protocol succeeds. Agent POST /agent/v1/switches/{id}/checkins accepts a signed message and returns a signed receipt. Agent GET /agent/v1/public/switches/{id} returns the manifest and permitted release material. GET /api/v1/switches/{id} returns confirmed state, B0, Bmax, allowance assumptions, unresolved issued requests, and per-agent evidence. CLI: epochalypse switch create, arm, checkin, status, export, and recover. The protocol review defines exact body fields and boundary semantics before these routes ship.

The API uses the shared error format in the project spec. Mutations require owner authorization unless this file states otherwise.

Edge cases & failures

A network partition can trigger release despite an available owner. Explain this before arm confirmation. An uncertain renewal never shows a green success state or a definitive failure claim. A missing response does not prove rejection. Preserve unresolved intent across client restart. An unavailable agent prevents full renewal. Two available agents still support release under the reviewed fault model. A disk rollback or excessive clock uncertainty removes the agent from readiness until the reviewed recovery procedure completes.

Out of scope

Email or SMS delivery, automatic proof of death, anonymous agent enrollment, and guaranteed recovery after all agents disappear.
